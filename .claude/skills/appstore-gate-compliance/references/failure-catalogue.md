# Failure catalogue: the thirteen-failure App Store cycle, root-caused

Deep reference for the `appstore-gate-compliance` skill. Read this when diagnosing a
specific pipeline failure or when you want the full root-cause narrative behind a
checklist item; the skill's own checklist, decision rules, and standards already carry
the fixes in condensed form, so you do not need this file to scaffold a compliant app.

The failure classes map one-to-one onto the pipeline's stages, in order, because each
stage only runs once the previous one passes: Install and Test (Failures 1 to 5), Code
Quality (Failure 6), the image policy scan (Failures 8 to 10), and Deploy (Failures 11
to 13), with a prior-cycle console-state failure (Failure 7) and an app-record residue
class (zero stages run).

## Failure 1: test suite excluded from the package (died in eight seconds)

● **Symptom**: `Cannot find module '.../tests/run.js'`; downstream stages skipped.
● **Root cause**: the packaging script shipped source and the Dockerfile but banned `tests/` and `docs/`, inherited from the previous static-html archetype where the package is a built artefact and shipping tests is correctly forbidden. The archetype pivoted; the packaging assumption did not.
● **Fix**: ship `tests/`, `docs/`, and the test-runner config in the source zip; keep them out of the image via `.dockerignore`. The package contract and the image contract are different layers with different exclusion lists (`packaging`).
● **Prevention rule**: when an archetype changes, re-derive the packaging allowlist from the new platform contract. Never carry an exclusion list across an archetype boundary.

## Failure 2: test orchestrator assumed a prior build

● **Symptom**: the audit, accessibility, and performance suites all read a built `dist/`, and the platform pipeline has no build step of its own.
● **Fix**: the orchestrator checks for the built artefact at startup and runs the build itself when it is absent. One guard, top of file, runs once.
● **Prevention rule**: `npm test` in a fresh clone with only an install step before it must pass; if any suite reads a generated artefact, the orchestrator owns generating it (`testing-standards`).

## Failure 3: security scan fail-opened on a registry outage (found by adversarial review)

● **Symptom**: with the advisory endpoint unreachable, `npm audit --json` on npm 8 and later returns an error-shaped object on stdout with **exit code 0** (a `message` or `error` field and no `metadata`). Naive parsing reads that as a clean, zero-advisory report; a tree carrying a real High advisory scanned as clean.
● **Fix**: detect the error shape first (JSON present, `metadata` absent) and route it as a failure to check. Split by runner: an offline runner may report an honest skip; the networked CI runner must hard-fail, because a skip there means both gates soft-pass at once. Apply the guard to every scan call site, including a re-scan after an auto-fix.
● **Prevention rule**: enumerate a scanner's failure output shapes before trusting its output; exit code alone is not a contract. A gate that cannot run degrades to an honest skip or a hard fail, never a silent pass (`dependencies`, `security-hardening`).

## Failure 4: a baked environment default defeated the platform's injected value (found by adversarial review)

● **Symptom**: the file-storage add-on injects `STORAGE_MOUNT_PATH` at deploy time. The code chain was `DATA_DIR || STORAGE_MOUNT_PATH || '/data'`, but the Dockerfile baked `ENV DATA_DIR=/data`, so the injected mount was dead code and writes landed on the ephemeral layer: fully functional, invisible in every test, lost on redeploy.
● **Fix**: never bake a path or port the platform injects. Set defaults in code; validate the resolved value at boot (absolute, not root, writable) and fail closed with a clear message.
● **Prevention rule**: for every auto-injected variable (`STORAGE_MOUNT_PATH`, `PORT`, `CLAMAV_HOST`) decide explicitly to consume, fall back, or ignore, and record it as a comment plus a boot validation. An `ENV` line always beats a fallback chain, so diff the Dockerfile `ENV` block against every fallback chain in code (`app-store-deployment`, `security-hardening`).

## Failure 5: an environment assertion false on the platform's checkout (218 of 219 passed)

● **Symptom**: the corrected package ran the entire suite on the platform for the first time and failed on exactly one audit assertion: "no `.gitlab-ci.yml` at repo root".
● **Root cause**: the rule protects the app's own repository and is correct there, but the platform checks out a project where it has committed exactly that generated file. The assertion was guaranteed-false only in the environment that gates the deploy; a rule and its enforcement context had been conflated.
● **Fix**: gate the assertion on the runner's identity (`GITLAB_CI` is set by every GitLab runner). On the platform, record the file's presence as an explicit, honest pass; locally and in the app's own CI the absence check still fails loudly.
● **Prevention rule**: audit every negative assertion against the deploy environment, not just the development one. Enumerate what the platform adds (`.gitlab-ci.yml`, `GITLAB_CI`, injected add-on variables) and classify each assertion as ours-only or everywhere; grep the suite for negative file-existence checks to sweep them (`testing-standards`).

## Failure 6: the SonarQube quality gate (five successive waves, 620 to 2 open violations)

● **Symptom**: the pipeline reached Code Quality for the first time and failed on all four thresholds: coverage 0.0% (required 80%), 620 violations, security hotspots, and ratings over cap. Clearing it took five scans.
● **Root cause (coverage)**: a thorough suite (500-plus assertions) emitted no machine-readable report, so the gate read 0%. Test quality and measured coverage are different artefacts; the gate reads only the artefact.
● **Root cause (violations)**: months of growth with no static-analysis loop left Sonar's defaults (cognitive complexity 15 per function, loop shapes, comparators, ARIA and contrast rules) with 620 accumulated hits, including a function at complexity 146.
● **Fix (coverage)**: pin a coverage tool (c8 for Node); the orchestrator re-execs itself under the tool when `--coverage` is present, emitting `coverage/lcov.info`, and child suites inherit `NODE_V8_COVERAGE`. Commit `sonar-project.properties` declaring sources, tests, the lcov path, and exclusions. Where a metric cannot be measured honestly (a concatenated bundle tested through jsdom cannot attribute per-file lines), exclude it from the COVERAGE metric only, never from analysis, with the rationale written in the properties file.
● **Fix (violations)**: fix everything, mechanically where possible. Cognitive-complexity findings resolve by extraction into named helpers with no behaviour change; in a shared-global-scope bundle every helper needs a unique module prefix, and functions extracted by a `vm`-based test harness must keep their helpers nested inside the extracted function or the sandbox loses them. Security hotspots resolve by fixing the code (de-backtrack a regex, swap `Math.random` for `crypto.getRandomValues`), not by dashboard review an uploader cannot perform.

The quality gate does not converge in one pass; four properties of it, each a lesson:

● **Progressive rule revelation.** The profile reveals rules progressively across scans: a later wave was almost entirely classes no earlier scan had mentioned (`node:` import protocol, `Number.parseInt`/`Number.isNaN`, `String#replaceAll`, `.at(-N)`, `structuredClone`, `globalThis`, explicit catch handling, floating promises, dialog and output role semantics, fresh contrast findings). Plan three to five upload cycles when retrofitting, or run a comprehensive modern lint profile (the unicorn and sonarjs ESLint plugin sets approximate it) locally from day one.
● **A findings report is a sample, not the population.** Sonar lists a page per scan, and new code (your wave-1 helpers) is rescanned too. Fix by RULE CLASS, repo-wide, the moment a rule fires anywhere, and measure the population directly with residual greps or a local analyser rather than fixing only the reported lines. Class-by-report fixing shrank the tail slowly (620 to 482 to 327 to 115); a grep-verified eradication wave collapsed it, and the fifth scan still found two the greps' spellings had missed.
● **Eradication greps must cover every syntactic spelling, and respect each rule's exemptions.** A rule has several spellings (positive and negated, guard and expression, read-only and read-write loops); the residual set must enumerate them all. The tail was an optional-chain candidate in the `!x || !x.method()` form (the greps had swept `x && x.y`) and an index loop the for-of rule flags but which is exempt when the index is used beyond element access.
● **A mandated fix from one wave becomes the next wave's finding.** Wave 3's empty-catch and floating-promise rules mandated adding `.catch`; the next wave's S4822 then flagged a `try`/`catch` wrapped around a promise that already carries `.catch` as dead rejection-path code. Resolve structurally, not additively: decide where each async call's rejection handling lives (one place) and remove the other layer, never both. When a sweep adds a pattern everywhere, that pattern is new code the next scan analyses.

Mechanical swaps carry semantic traps; prove behaviour preservation over hostile inputs, not just the existing suite (`code-architecture`, `testing-standards`): `Number.isNaN` does not coerce (wrap Date arguments in `Number()`); `structuredClone` preserves Dates a JSON round-trip stringified, and is absent from jsdom; `| 0` in a PRNG is a 32-bit wrap, not a truncation (`% 4294967296` is congruent forever; a `Math.trunc` swap diverged after millions of draws); `localeCompare` is not the default code-unit sort order; `x && x.y` to `x?.y` changes the produced value from the falsy left operand to `undefined`; and `String.replace` templating must use the callback form, because dollar sequences in the inserted content splice file context into the output.

● **Prevention rules**: wire coverage output and a static-analysis loop at scaffold time when the count is zero, not at upload time when it is 620; run the same analyser locally or in CI that the platform runs, with the same profile (`ci-cd`); treat "my tests are comprehensive" and "the gate can see my coverage" as independent claims, verified by reading the lcov file (`testing-standards`); and prove every metric refactor behaviour-preserving with parity harnesses and a render smoke.

## Failure 7 (prior cycle, same theme): stale platform configuration survived an archetype pivot

● **Symptom**: the app's Environment Variables tab still carried storage variables from the static-html era; the operator had no way to know they were dead.
● **Fix**: on any archetype change, produce an explicit "platform console changes" list for the operator: variables to delete, add-ons to enable, fields that changed meaning. The code change is not the whole change. On the FIRST delivery of a container app, make this a full deployment parameters table (template, the port and `PORT` contract, every environment variable and its source, add-ons and the variables they inject, `securityContext.fsGroup` where applicable, the resource budget, the health paths) so the operator configures the platform from one source (`release-and-deploy`).

## Failure 8: the image policy scan flags the base image, not your code

● **Symptom**: with Code Quality green, the image scan ran for the first time and failed: hundreds of critical `suid_or_guid_set` findings plus dependency advisories (picomatch, sigstore, tar, busybox). Not one was in project code; the app has zero runtime dependencies.
● **Root cause**: the stock `node:*-alpine` runtime ships the npm command-line tool, whose vendored dependencies carry the advisories, and base-image files with setuid/setgid bits, which the policy counts as criticals. A container that only ever runs `node server.js` still ships a package manager and privilege-escalation flags it never uses, and the scanner judges what ships, not what runs.
● **Fix**: three runtime-stage steps. (1) Remove the toolchain entirely (`rm -rf` the global `node_modules`, `npm`, `npx`, `corepack`, `yarn`; the build stage keeps npm for the install). (2) Strip every suid/sgid bit from files AND directories (`find / -xdev -perm /6000 -type f -exec chmod a-s {} +`, then `-type d`), fail closed, ordered after any `apk upgrade` so a reinstall cannot reintroduce a bit; safe because a non-root service on an unprivileged port never needs suid. (3) Best-effort `apk upgrade` for base-package mediums, fail-open and confined to its OWN RUN instruction so it can never mask the two fail-closed steps.
● **Prevention rules**: harden the runtime stage at scaffold time (no package manager, no suid/sgid bits, upgraded base, non-root, ships nothing the CMD does not need); read the package names before touching your code, because base-image findings need a Dockerfile fix, not an application change; keep fail-open and fail-closed steps in SEPARATE RUN instructions; and when the sandbox cannot build the image (registry blocked), verify path assumptions against the upstream base image and construct every load-bearing step to fail the platform build loudly if an assumption is wrong (`security-hardening`, `deploy-recipes`).

## Failure 9: the image scanner reads layer history, so an in-place fix cannot fully clear it

● **Symptom**: the rescan of the Failure 8 fix showed every toolchain advisory gone and the suid criticals down from hundreds to a residue, all path-less (`N/A`), beside only unpatched-upstream busybox mediums.
● **Root cause**: a container image is a stack of immutable layers, and the suid/sgid check inspects layer blobs. A `chmod` in a later layer masks the file in the final filesystem, but the base image's earlier layers still physically contain the original files with their bits set, and the scanner reads them there. You cannot edit layer history; you can only stop shipping it.
● **Fix**: flatten the runtime into a single, already-clean layer. Do all hygiene (upgrade, toolchain removal, suid sweep, app file copies) in a `prep` stage, then make the shipped stage `FROM scratch` with exactly one `COPY --from=prep / /`. The COPY takes the prep stage's final filesystem view with modes, ownership, and symlinks preserved, so the distributed image has one layer and no history. Re-declare all metadata in the scratch stage (WORKDIR, VOLUME, ENV, USER, EXPOSE, HEALTHCHECK, CMD) because image config does not travel through COPY, and set `PATH` explicitly since scratch carries no base config to inherit it from. `/etc/passwd` travels in the COPY so a named USER resolves (a numeric USER resolves regardless). Sweep directories as well as files (`-type f` misses setgid directories); leave the sticky bit alone so `/tmp` stays 1777.
● **Prevention rules**: treat "fixed in the final filesystem" and "absent from the distributed image" as different claims; a layer-aware scanner tests the second, and the flatten satisfies both by construction, so make it the scaffold-time default for any image facing a policy scanner. When a partial fix moves a count rather than zeroing it, the residue is telling you about the scanner's mechanism, not about missed files; diagnose the mechanism before fixing again.

## Failure 10: your own later instruction re-introduces the class the sweep just cleared

● **Symptom**: the flattened image scanned with exactly one critical, and the raw job log (the failure summary printed `N/A` for every path) named it precisely: `SUID or SGID found set on file /home/app. Mode: 0o42755`.
● **Root cause**: busybox `adduser` creates the non-root user's home directory with the setgid bit, and the Dockerfile ran the suid/sgid sweep BEFORE user creation. The finding was neither the base image nor layer history; it was our own later instruction re-introducing the class the sweep had just cleared.
● **Fix**: make the sweep the LAST mutation in the prep stage, after user creation and the application file copies, immediately before the flatten. One fail-closed line covers files and directories: `find / -xdev -perm /6000 \( -type f -o -type d \) -exec chmod a-s {} +`. Removing setgid from the home directory is free here (nothing in the runtime writes under `/home`).
● **Prevention rules**: any invariant a sweep establishes holds only from that instruction onwards, so place invariant-establishing steps LAST in the stage and audit each later instruction (`adduser` sets setgid on the home it creates; package installs can ship suid binaries). The failure SUMMARY and the raw JOB LOG are different documents: obtain the raw log before theorising (it named the file and mode where the summary showed `N/A`), and when a hypothesis and a log line disagree, the log line wins. The raw log also settles policy: the scan tests the `/6000` mask only (leave `/tmp` sticky at 1777), and medium findings carry action `warn`, not `stop` (they never block approval).

## Failure 11: guidance text pasted as an environment-variable value (deploy stage)

● **Symptom**: every pipeline stage green, but the app pod crash-looped: `fatal boot error: data dir must be an absolute path below the filesystem root; got "whatever STORAGE_MOUNT_PATH reveals as (for example /mnt/storage)"`. The sibling add-on pod (ClamAV) was healthy, so the deployment machinery was fine. It recurred: the same prose sat in a SECOND variable (a manually created `STORAGE_MOUNT_PATH`, which the platform injects at the pod level and should never be typed into the tab).
● **Root cause**: the operator's Environment Variables tab held a literal sentence of guidance text as a variable value, pasted from an earlier explanation. The app's fail-closed boot validation refused it exactly as designed and quoted the received value verbatim.
● **Fix**: console-only, delete the variable; the code's resolution chain (explicit var, then the platform-injected `STORAGE_MOUNT_PATH`, then the default) takes over. Harden the guard itself so the rejection NAMES the source ("got X from the STORAGE_MOUNT_PATH environment variable") and states the remedy; pin the rejection path with committed tests.
● **Prevention rules**: every value in operator console instructions must be COPY-PASTE EXACT or explicitly "delete this variable", never a descriptive placeholder ("whatever X is", "your path here") near a paste-able field, and assume anything pasted once was pasted into every field the guidance mentioned. Boot validation must echo the rejected value AND name the source AND state the fix. The correct console state for an app with code defaults is an EMPTY environment tab; platform-injected variables live at the pod level, so anything typed into the tab is an override and a liability. A crash-looping app pod beside healthy add-on pods means configuration, not infrastructure; read the pod log first (`release-and-deploy`, `security-hardening`).

## Failure 12: the mounted volume refuses writes from a non-root container (deploy stage, platform-side)

● **Symptom**: the app served its SPA (server up) but `/healthz` returned 503 and the splash refused to proceed. Pod log: `storage.ready-probe-failed ... EACCES: permission denied, open '/mnt/storage/.readyz.tmp'`.
● **Root cause**: the platform contract demands a non-root container AND the file-storage add-on mounts a root-owned volume, and the generated pod spec sets no `securityContext.fsGroup`, so the kubelet never makes the mount group-writable. The two platform requirements contradict each other for any non-root workload; nothing in the app, the zip, or the Dockerfile can fix it.
● **Fix**: an operations request, quoting the errno line, to set `securityContext.fsGroup` (any fixed group id) on the app's deployment so mounted volumes are group-writable to non-root containers. It is platform-general: every non-root container using the add-on hits it.
● **Prevention rules**: distinguish "server up but store unwritable" (healthz 503, SPA serves) from "server down" (crash loop): `mkdir` on an existing dir succeeds without write permission, so always health-check with a real WRITE, never an existence check. Make the health endpoint self-diagnosing, record the last probe error and return the resolved data dir and the exact errno in the 503 body, and render both in the client's failure banner, so a screenshot is a complete diagnosis without pod-log access. A pod log can interleave MULTIPLE pod generations; attribute each line to its generation before concluding. Escape server strings at the client sink even when trusted today: the binding security gate FAILED this release on an unescaped `innerHTML` interpolation the new diagnosis fed; the one-escaper rule is about the sink, not today's source (`observability-and-audit`, `frontend-and-rendering`, `security-hardening`).

## Failure 13: the pod dies seconds after a clean boot and the log says nothing (deploy stage)

● **Symptom**: the pod logged `server-listening`, then `shutdown-requested SIGTERM` 36 seconds later with zero lines between; the SAME pod name restarted with growing gaps (kubelet liveness back-off). The sibling ClamAV pod stayed healthy.
● **Root cause class**: a health probe that HANGS rather than fails. A stalled network volume blocks the probe's test write forever: no exception, no log line, and the platform's health check times out silently and kills a container that looks perfectly healthy in its own log.
● **Fix (make the app incapable of dying silently)**: the readiness probe races a hard timeout (2 seconds) via `Promise.race`, with every rejection converted to a value so a late-settling hung probe can never become an unhandled rejection, and reports an honest "the volume mount may be unresponsive" reason on timeout; boot emits one decisive log line recording whether storage accepted a write at pod start; ready and unready transitions log, so the pod log reads as a narrative.
● **Prevention rules**: every health probe must have a TIMEOUT strictly shorter than the platform's probe timeout; a probe that can hang converts an infrastructure fault into an undiagnosable silent kill. Log the health verdict at boot, once, unconditionally; a pod log whose only line is "listening" proves nothing about the thing the platform judges. The same pod name restarting with growing gaps is kubelet liveness back-off; a new pod name each time is the deployment controller, read which before theorising. A healthy sibling add-on pod localises the fault to the app container's probe loop (`observability-and-audit`, `api-and-integration`).

## App-record residue (zero stages run)

● Deleting and recreating an App Store app can orphan its records and its GitLab project, and a slug containing a double hyphen can break platform naming; both present as a pipeline that fails with ZERO stages run (distinct from a stage failing). Recreate under a fresh, single-hyphen slug and confirm the old records are cleared (`app-store-deployment`).
